What each core supports.

Three tables — one per emulated core — listing every feature area, what was done, what is still missing, and the remark that explains the gap. Status words mean: done (verified), partial (works with known limits), missing (not modeled).

425 tests native + WASM agree A and B packages both run
RP2350A or RP2350B — do we support them? Yes, both. The A/B split is packaging, not silicon: the same die in a 60-pin package (30 GPIO, 4 ADC channels, 16 PWM channels) or an 80-pin package (48 GPIO, 8 ADC, 24 PWM). Bramble models the full die — 48 GPIO, 8 ADC channels, 16 DMA channels, 3 PIO blocks — so A-package firmware runs unchanged and the extra B pins stay idle. RP2354 variants (stacked 2 MB flash) behave like external flash here: capacity is configurable up to 16 MB.

Guides

Wired Ethernet: is there any on these chips?

Neither the RP2040 nor the RP2350 has an on-chip Ethernet MAC — there is nothing to route to pins, on any package. Boards that advertise Ethernet with these chips always add a separate controller over SPI. The boards you have seen are almost certainly WIZnet W5500 designs (hardwired TCP/IP stack, very common on Pico-shaped Ethernet hats) or, less often, Microchip ENC28J60 or LAN8720 PHY boards.

Bramble emulates the W5500 itself as an SPI device (src/w5500.c): 8 sockets with 2 KB TX/RX buffers each, register-level compatible, with a live mode (-net-live natively, WebSocket proxy in the browser) that dials real host TCP/UDP sockets. So W5500-based firmware and carrier boards work here; what is modeled is the external chip, not silicon Ethernet — because the silicon has none.

pico-eth board: WIZnet W5500-EVB-Pico (and Pico2)

The legacy -net-live device floats on the SPI bus with no board pins. The pico-eth board variant models the actual WIZnet W5500-EVB-Pico carrier: the same W5500 on SPI0 (SCK 18 / MOSI 19 / MISO 16, mode 0/3) with CSn = GPIO17, RSTn = GPIO20, INTn = GPIO21 (active-low). Firmware bit-bangs CSn/RSTn as GPIOs and polls or waits on INTn exactly like on hardware; VERSIONR reads 0x04, socket IR bits are write-1-to-clear, and SIR is computed from live socket state.

Native: ./build/bramble firmware.uf2 -board pico-eth for the stub (instant ESTABLISHED, no host sockets), plus -board-live to dial real host TCP/UDP, -board-spi 0|1 to move the board (default 0). Explicit -sdcard/-emmc flags win the SPI slot on conflict. Browser bench: pick pico-eth in the Board row (SPI + live tickbox); Node: node web/cli.js firmware.uf2 --board pico-eth --board-live. Off by default with zero cost: one flag test in the GPIO/poll hooks, no device attached, no sockets polled.

Version 2? Yes — pico-eth2 is an accepted alias for the RP2350-based WIZnet W5500-EVB-Pico2. It selects the identical model: WIZnet kept the exact same wiring and pins on the Pico2 board (verified against their docs, the Zephyr board DTS, and the MicroPython board ports), so only the SoC changes. On M33/RV32 firmware the RP2350 SPI bases (0x40080000/0x40088000) route to the same SPI instances; GPIO17/20/21 behave identically (SIO base is unchanged at 0xD0000000).

Run firmware

Native: cmake -S . -B build && cmake --build build -j, then ./build/bramble firmware.uf2 -clock 125. Add -stdin for interactive shells, -wifi for the CYW43, -gdb for remote debugging. The browser bench mirrors every flag with a control on the page.

Browser and Node

./build_wasm.sh produces the WASM pair; serve web/ over HTTP and open the bench, or drive it headless with node test-wasm.js and node test-mp-ble-live.mjs. The -pthread threads build needs cross-origin isolation (python3 web/serve_coop.py).

Networking and Bluetooth

Virtual Ethernet (-net, -net-peer), live sockets (-net-live, web/net_proxy.py), gateway NAT64/DNS64, and BLE either internally (advertise, scan room, GATT loopback) or forwarded to Bumble/RootCanal/physical adapters (-bt-hci, web/hci_bridge.py). Details live in docs/NETWORKING.md and docs/GATEWAY.md.

WASM networking: one gateway for WiFi + Ethernet

Yes — WASM fully emulates the W5500 chip (same src/w5500.c registers, sockets, and SPI framing as native). There is a single gateway: socket 0 in MACRAW mode joins the same vnet bus as CYW43, so guest DHCP/ARP/IP flow as raw Ethernet frames to the same Go gateway (ws://host:5090/api/network-gateway), same room, same DHCP pool. Browser: tick Ethernet via gateway (default on) and open the Gateway panel; the per-frame pump forwards bramble_eth_pop_tx() both ways automatically. Node: pass --gateway … — no proxy sockets needed for the gateway path.

The older per-socket /w5500 proxy path (web/net_proxy.py dialing host TCP/UDP per socket) still exists for offload sockets 1–7, but it is not a second gateway: it bypasses DHCP/rooms by design. Prefer MACRAW. Full matrix — DHCP, ARP, coexistence, RP2350 — lives in docs/NETWORKING.md under “Ethernet (W5500 MACRAW) support matrix”.
